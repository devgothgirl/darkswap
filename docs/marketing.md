# Marketing opt-in and campaigns

The signup endpoint `POST /api/marketing/subscriptions` accepts **only** `{ "email": "...", "consent": true }` and returns `{ "message": "..." }`. It sends a confirmation email only when the signed webhook is configured and explicitly marked ready; repeat requests for the same unverified address have a database-backed 15-minute cooldown. It does not enroll a contact until a human submits the form at `GET /api/marketing/confirm?token=...` via `POST /api/marketing/confirm` with `token` in the body. Tokens expire in 24 hours and only SHA-256 hashes are stored. Earlier contacts have `verified_at = NULL` and are ineligible until confirming.

Every message includes a usable unsubscribe URL and one-click list-unsubscribe headers. `GET /api/marketing/unsubscribe?token=...` displays a form but does not alter state; `POST /api/marketing/unsubscribe?token=...` accepts the RFC 8058 `List-Unsubscribe=One-Click` body without a token field (the form also accepts `token` in a URL-encoded or JSON body), and is permanently idempotent. Token pages set no-referrer, no-store and restrictive CSP headers. A previously unsubscribed or provider-suppressed contact cannot re-enroll from the signup endpoint. Do not put tokens in logs or analytics.

Configure `MARKETING_PUBLIC_URL=https://darkswap.app`, `MARKETING_FROM_EMAIL` (verified Resend sender), `MARKETING_POSTAL_ADDRESS` (real physical mailing address), and stable random `MARKETING_UNSUBSCRIBE_SECRET` (at least 32 characters). No sends occur without all four. Campaign sends also require `MARKETING_RESEND_WEBHOOK_SECRET` (the Resend webhook signing secret beginning `whsec_`) and `MARKETING_WEBHOOK_READY=true` **only after** verifying the Resend dashboard webhook delivers signed `email.sent`, `email.bounced` and `email.complained` events to `https://darkswap.app/api/marketing/webhook/resend`. `email.delivered` may also be enabled. The connected Resend send-only credential cannot retrieve events. Webhook signatures, timestamps and event identifiers are verified; events received before delivery ID persistence are kept and applied afterward.

`GET /api/marketing/health` returns 200 only while the gate is configured, a signed event linked to a marketing delivery arrived in the last 24 hours, no monitored accepted delivery has remained unacknowledged for 15 minutes, and no signed webhook processing failure is latched. Older deliveries predating this check are not retrospectively treated as overdue. Otherwise it returns 503 with a status code (`not_ready`, `stale`, `backlog`, `processing_failure`, or `unavailable`); it never exposes contacts or provider identifiers. An overdue backlog latches the pause even if the delayed event subsequently arrives. Accepted deliveries retain a durable webhook acknowledgment; the server backfills acknowledgments from existing receipts before deleting receipts older than 30 days on startup and daily thereafter. Unmatched early receipts have a 30-day matching window. Recent correlated receipts are still required to demonstrate live webhook health. Configure an external uptime alert on non-200 responses, and monitor the fixed-text server health-transition/error logs. This is separate from swap health. Campaign sending checks health at the start and before **each** provider call; dry runs do not need a healthy webhook. A quiet mailing list eventually becomes `stale` even if the endpoint still works: set `MARKETING_WEBHOOK_PROBE_EMAIL` to an operator-controlled mailbox and run `pnpm --dir scripts exec tsx ../artifacts/api-server/src/lib/marketing-cli.ts --probe`; verify the signed `email.sent` receipt restores health before sending. The probe never uses subscriber data. If a processing failure is latched, investigate and reconcile missing bounce/complaint events **before** clearing the row in `marketing_webhook_status` with key `resend`; a successful later event does not automatically clear it. If the database was unavailable when a webhook failed, set `MARKETING_WEBHOOK_READY=false` until missed events are reconciled even if health later returns healthy. Never clear the latch merely to restart a campaign. No check can detect a provider dropping only bounce/complaint events while continuing to deliver `email.sent`; periodically verify all subscribed event types in the Resend dashboard. No campaign should run until the additive schema is applied. No contacts, tokens or bodies belong in monitoring or alerts.

### Durable processing pause and reconciliation

Each authenticated callback claims a write-ahead row in `marketing_webhook_processing` **before** parsing or applying the event. It contains only an attempt UUID, signed event ID and start time, not contacts or payloads. Claims use the shared database transaction advisory gate: if any row already exists for that signed event ID, the replay returns 503 without applying the payload, adding another row, refreshing the start time, or setting a new failure latch. Active overlaps therefore do not create a permanent false failure; failed or interrupted attempts continue to require reconciliation. New unresolved attempts are bounded to one row per signed event ID, not one per retry. Distinct events retain independent fences. Existing duplicate rows from older workers are preserved, not compacted automatically, and also prevent new claims for their event. Drain/restart all old callback workers during rollout; mixed-version workers can still add legacy duplicate rows.

If a new fence cannot be committed, processing is refused with 503. A successful owner deletes only its own attempt UUID. A processing failure, rejected failure-latch write, failed cleanup, or worker crash leaves its row intact. Any remaining row blocks campaign sends across all workers and restarts, even with fresh healthy receipts. In-progress callbacks also temporarily pause campaigns. A successful replay cannot take ownership of or remove an earlier failed attempt's row, even if it supplies a corrected payload. After explicit reconciliation removes all reviewed rows for that event, a later callback may claim a new attempt UUID; cleanup using an older UUID cannot clear that new attempt. There is no automatic expiry or limit that drops unresolved distinct events.

For recovery, first disable campaign readiness in every sender and wait for active callback attempts to settle. Review outstanding attempt IDs and their signed event IDs in the correct environment's database. Use the provider's event history to reconcile missing bounce/complaint suppressions and delivery receipts, including events whose processing was refused. Do not delete active or unreviewed attempts and do not expire these rows automatically. Only after that review, explicitly delete the **specific reviewed attempt UUIDs** from `marketing_webhook_processing` and clear the `resend` row in `marketing_webhook_status` if its failure was also reconciled. Restart workers whose local fallback was set by a rejected latch write, verify a controlled probe and health, then re-enable readiness. Restarting, repairing database writes, or receiving a later valid callback is not reconciliation.

Apply the Drizzle schema with the main agent's coordinated database push; **do not force-push or reset data**. The additive `marketing_webhook_processing` table must exist before processing callbacks or enabling campaign sends; if it is absent, those operations fail closed. Additive nullable columns preserve old contacts as unverified. Campaign reservations have a unique `(campaign_key, email)` constraint, and a campaign key is permanently bound to the SHA-256 hash of its subject/HTML/text. Changed content under the same key fails rather than accidentally sending a mixed campaign. Once a send has been attempted, retries never send it again automatically even when the provider reply is lost. A dry run counts eligible unreserved recipients without sending and is not a guarantee of later eligibility. Real sends recheck eligibility before each recipient and wait at least 600 ms between attempts in one CLI invocation. Signed webhook recipient addresses are suppressed only when they strictly match an existing marketing contact, including when a provider reply is lost.

Campaign JSON: `{ "key": "unique-campaign-id", "subject": "Your subject", "html": "<p>Content</p>", "text": "Content" }`. Use a new stable key for each campaign; changing content under an existing key will not resend previously attempted contacts. Run from the workspace root:

```sh
pnpm --dir scripts exec tsx ../artifacts/api-server/src/lib/marketing-cli.ts campaign.json
# After reviewing the dry run and message:
pnpm --dir scripts exec tsx ../artifacts/api-server/src/lib/marketing-cli.ts campaign.json --send --confirm=unique-campaign-id
```

Run database-backed tests only **after** schema push: `pnpm --dir scripts exec tsx --test ../artifacts/api-server/src/lib/marketing.db.test.ts`. They use a mock transport, unique `.invalid` addresses, and delete exactly their seeded rows in `finally`; no test sends provider email. The SDK dependency `@replit/connectors-sdk` must be available to the API server. Never associate these contacts with orders, wallets, or transactions.
