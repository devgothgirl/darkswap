# SplitWise live-route assessment

Assessment date: 2026-09-27. **Decision: keep SplitWise a browser-only planning preview. Do not enable order creation, deposits, wallet signing, or transfers from this page.** The provider publishes a multi-swap contract, but its own partner FAQ contradicts the multi-swap guide about public API availability. Neither account entitlement nor a quote-to-execution binding for this product has been established. No live multi-order request or transfer was made for this assessment.

## Contract evidence and current limits

| Capability | Verified published contract | What DarkSwap can safely claim now |
| --- | --- | --- |
| Single private route | [Private swap flow](https://docs.houdiniswap.com/developer-hub/swap-flows/private-swap): `GET /v2/quotes?from=...&to=...&amount=...&types=private` yields a `quoteId`; `POST /v2/exchanges` takes `quoteId` and **one** `addressTo`; `GET /v2/orders/{houdiniId}` tracks the order. The existing `/api/swap/*` server implements this single-recipient route. | A separate live private swap exists, not a multi-recipient SplitWise transfer. It requires an exact manual deposit to the returned address; creating the order does not move funds. |
| Batch recipients | The [multi-swap guide](https://docs.houdiniswap.com/developer-hub/swap-flows/multi-swap) and [live v2 OpenAPI](https://api-partner.houdiniswap.com/v2/openapi.json) (observed version 2.1.2) describe `POST /v2/exchanges/multi` with 1–50 `orders`, each having `from`, `to`, `amount`, `addressTo`, optional `anonymous`, memo and refund fields. It returns `multiId` and per-item `order` **or** `error`, followed by `GET /v2/exchanges/multi/{multiId}`. Private/CEX routing is described; DEX orders are not supported. The [partner FAQ](https://docs.houdiniswap.com/partner-faqs), however, explicitly says multi-swap is **not currently available via the public API**. | Published schema is not proof this account can create multi-orders. Treat availability as **unconfirmed** until provider confirmation and an authorized non-funding integration check resolve the contradiction. Do not represent a 500-row preview as a supported 500-order batch; the published create limit is 50. |
| Batch quotes and fees | OpenAPI describes `POST /v2/quotes/multi` with 1–10 orders and `mode=all` for individual candidate quotes (`mode=single` only quotes the first). Quote candidates expose `amountIn`, `amountOut`, `feeUsd`, `gasUsd`, `bridgeFeeUsd`, `min`, `max`, `validUntil`, `fixed` and error/filter fields. Multi-order **creation** uses `from`/`to`/`amount`/`addressTo`, not a selected `quoteId`; it prices orders independently. | No final per-recipient output, total fee, min/max, quote expiry or batch price guarantee is available on SplitWise. In particular, do not treat a prior multi-quote as binding a later batch create. Requote and compare actual per-order creation amounts before any funding; surface network fees and any partner markup separately. Larger batches need chunked quotes and new validation, never an assumed single aggregate quote. |
| Exchange/provider selection | OpenAPI `QuoteFilters` has `onlySwaps`, `inLeg.include/exclude`, `outLeg.include/exclude`, rotation and deviation options; batch quote/create accept **top-level filters applied to every order**. `GET /v2/quotes` also offers in/out-leg filters for private routes. | The preview's free-text `exchange` / route note is not a provider ID or selection. No per-recipient provider control is verified on the supported batch request (the per-order filters alias is marked deprecated). Validate identifiers against a fresh provider list and show actual selected routes before promising any user choice. Provider fallback/rotation may change execution venue. |
| Solana funding | The [multi-swap guide](https://docs.houdiniswap.com/developer-hub/swap-flows/multi-swap) describes `GET /v2/exchanges/multi/{multiId}/tx?sender=...` for same-Solana-source-token orders: serialized transactions cover at most **10 orders each**, with more than 10 requiring multiple independent signatures/submissions. Each order has its own deposit address, status and expiry. | This is a proposed wallet-authorized funding path, **not** implemented in DarkSwap. It is not one atomic payment across all recipients. The current SplitWise address format check covers only Solana and is insufficient for arbitrary destination chains. |

These are published **contract limits**, not confirmed service capacity, chain/asset coverage, account access, minimum deposit or route availability. The source token must be a current CEX-supported Solana token ID; destination tokens and amounts must pass live provider checks. The preview's optional asset label, intended receive asset and arbitrary percentages are not token IDs or executable quote inputs. A percentage split additionally needs a real source amount, precision-aware rounding and a remainder policy. The provider's [overview](https://docs.houdiniswap.com/developer-hub/overview/what-you-can-build) also advertises multi-swap; the FAQ discrepancy remains unresolved.

## Conditions for a separate live flow (not a preview upgrade by implication)

1. **Provider/access gate:** obtain written confirmation of partner-account access to multi-quote, multi-create, status and Solana batch-tx endpoints and current rate limits. Confirm quote-vs-create pricing semantics, supported source/destination chains, provider filters, private-route behavior, geographic restrictions, refunds, idempotency/retries and allowed batch size. In a safe test environment, verify read-only token/quote responses and then use provider-approved test orders; never submit a real deposit just to establish capability.
2. **Security and compliance:** keep credentials and provider calls on the server; enforce authentication/authorization for any user-funded flow, CSRF protection, request limits, server-side token/address/network/memo validation, sanctions/geo and applicable AML controls, and avoid retaining unnecessary recipient or transaction data. The [partner FAQ](https://docs.houdiniswap.com/partner-faqs) says execution partners screen deposits and may freeze or reject them; this is not a privacy or settlement guarantee. Get legal/compliance review before marketing batch payouts or private routing.
3. **Fees and confirmation:** obtain fresh per-leg quotes and enforce amounts, limits, expiry, conversion, markup, fee and network-cost disclosure; account for rounding and price movement between quote and create. Require a distinct review screen with all recipients, networks, memos, send totals, expected/minimum receives, fees, route/privacy caveats, expiry and non-atomic partial-failure warning. A second explicit user action creates orders; after order creation show actual deposit instructions. For wallet funding require a further explicit signature for **each** transaction; verify serialized transaction instructions, recipients, amounts, mint, fee payer, blockhash and order-ID mapping before asking the wallet to sign. Never auto-fund from CSV import or draft review.
4. **Failure recovery:** persist only the minimum authorized batch/order identifiers and status mapping needed for recovery; make submission idempotent or reconcile timeouts before retrying. Creation may partly succeed; inspect each item and do not blindly retry successful legs. Wait for `INITIALIZING` to settle, track each order through expiry and completion, record signatures per batch transaction and show funded/unfunded/failed legs individually. On stale quote, expired deposit, wrong chain/memo, compliance hold, underpayment, or stuck order, stop funding, provide safe recovery instructions and a support escalation path using order IDs; never promise an automatic refund. Provider [multi-swap guide](https://docs.houdiniswap.com/developer-hub/swap-flows/multi-swap) and [partner FAQ](https://docs.houdiniswap.com/partner-faqs) describe partial failures, expiries and support escalation.

## Release decision

Keep `/splitwise-preview` and `/previews` labeled as planning-only. They currently make no provider calls, create no orders and cannot sign or send transactions; `/App.tsx` routes SplitWise only to that preview. Do not add a live CTA to this page or route the draft through the existing **single-recipient** `/api/swap/orders` endpoint. If provider access and the gates above are validated, build a separate live flow with a server-owned contract and explicit user review/funding states; keep the preview distinct until that flow is verified end to end.
